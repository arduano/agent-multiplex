# 04 — Exact native lifetime custody

The allocation owner retains one exact native subgroup/container and its opening
capsule. The original-operation journal introduced in03 will persist that capsule before
an agent launcher is allowed through. This layer owns resource retirement only;
it has no session inventory, effect queue, provider fallback or connection retry.

The Linux owning-service backend pins boot, service invocation, parent process,
delegated cgroup and inode/device identity. A one-shot gate waits for its exact
authenticated launcher. Stop seals acquisition and retires only that exact tree;
leader exit, quiet stdout, browser cancellation and transport loss do not prove
retirement. A dedicated Docker backend inspects an immutable owned container ID,
with no create retry or absence inference from an error message. The read-helper
path retains its separate purpose without acquiring native agent continuation.

Provenance: selectively retained allocation, cgroup and gate algorithms and their
actual-owner tests from reference61d90fd. The old transient-unit/legacy allocation
inspection fallback is removed. New allocation records start at version1; this
tree does not adopt previous deployment state. The structural contracts and public
entry are independent of lifecycle, harness, catalog and client implementations.

The decisive cases cover exact invocation replacement, unsafe service settings,
late gate readiness during Stop, sibling preservation, stale kernel identity,
reader custody and broken stdin without false process completion. Scripted
manager observations are not physical systemd/native qualification. The gate
tests use finite disposable Node children only; no vendor agent/model is used.

Validation is recorded after the03/04 checkpoint is built. Windows containment,
native crash-while-working and production reboot/fleet behavior remain unqualified.

The new delegated record version and attachment prefix are defined once in
`allocation-format.ts` and consumed by both allocation and the installed gate.
The reference format-2 compatibility assertion is retired along with its reader;
the retained custody oracle now asserts the new record version1. No old installed
state is adopted. Only the single public runtime entry is exported.

Checkpoint: source commit `206e252` archived independently (SHA-256
`6649b3b7f2b1f812b9de13f10715e07132a691f7f4fceae45008c9854baf7032`).
Its own locked install and `npm run check` passed strict types, all18 source
boundaries, all17 tests and a clean build. The eight runtime oracles include
finite real Node gate/launcher children, all reaped by their fixture cleanup;
the six manager cases are scripted kernel observations. There were zero native
vendor sessions, model calls, containers or service changes. This annotation is
documentation only; no future layer participated in that gate.

## CLI convention amendment

The internal gate source is `src/runtime/systemd-gate.ts`. Its explicit cmd-ts
subcommands are `gate` and `delegated-gate`; caller invocation arguments change
together in this layer. Help and rejected arguments never acquire custody. The
opaque allocation capsule, socket protocol, native argument passthrough and
positive Stop proof are unchanged. Scripted protocol fixtures are ordinary
generated JavaScript, rather than authored MJS tools.

## Contract placement amendment

Portable custody and allocation contracts live together in `contracts.ts`.
Platform inputs and command ports live in `node-contracts.ts`; the public
`runtime` facade exports both contract surfaces and the existing explicit owners.
`SystemdUserOptions` still requires the actual acquired `HostContainment` class,
and the backend still checks that handle with `instanceof` before accepting it.
The gate configuration remains an internal installed-helper format. This is a
contract relocation in layer04: proof identities, native acquisition/retirement,
platform command handlers, deadlines and resource custody remain unchanged.
